📘 O que é uma Pipeline RAG?

RAG (Retrieval-Augmented Generation) é uma técnica que combina busca inteligente com modelos de linguagem (LLMs) para gerar respostas baseadas em documentos específicos. Em vez de depender apenas do conhecimento pré-treinado da IA, a pipeline RAG permite que a IA consulte documentos corporativos em tempo real.

🎯 Objetivo da Pipeline NovaTech: Criar um assistente inteligente capaz de responder perguntas sobre políticas, procedimentos e SLAs da empresa usando apenas informações oficiais e rastreáveis, com suporte a versões conflitantes de documentos.

📥 Fase 1: Ingestão de Documentos

1
Script: indexar_documentos.py

🎯 Objetivo

Processar documentos Markdown, dividi-los em chunks semânticos, enriquecê-los para melhorar a busca, gerar embeddings e armazená-los no ChromaDB com metadados completos.

⚙️ Estratégia de Chunking: MarkdownHeaderTextSplitter

Splitter principal: MarkdownHeaderTextSplitter
• Cabeçalhos capturados: # (título), ## (seção), ### (subseção)
• strip_headers=False: mantém o título da seção no texto do chunk

Fallback (seções > 1200 chars): RecursiveCharacterTextSplitter
• chunk_size: 1200 caracteres  |  overlap: 200 caracteres

Por que MarkdownHeaderTextSplitter?

🗂️ Respeita a estrutura semântica dos documentos:

O RecursiveCharacterTextSplitter(size=500) original cortava seções no meio, independentemente do conteúdo. Exemplo real: a seção 3.2 da POL-001 ("Exceções ao prazo geral", ~865 chars) era dividida logo após o cabeçalho, entregando ao LLM apenas a primeira linha sem a lista de cargas nem o ramal 4500.

📌 strip_headers=False:

Preserva o título da seção no texto do chunk (ex: ### 3.2. Exceções ao prazo geral aparece no conteúdo). O modelo de embedding usa esse vocabulário para criar um vetor mais representativo do tema, melhorando a correspondência com queries sobre o mesmo assunto.

📏 Fallback em 1200 chars (não 800):

A seção 3.2 da POL-001 tem ~865 chars — com o limite em 800 ela era cortada em dois sub-chunks, fazendo o chunk com a lista ANTT (cargas perigosas classes 1–6) nunca ser recuperado. Com 1200 chars, todas as seções dos documentos NovaTech ficam como chunks únicos e íntegros.

🌍 Enriquecimento de Chunks

Dois enriquecimentos são aplicados antes do armazenamento para compensar as limitações semânticas do modelo de embedding inglês em documentos portugueses:

🗺️ Enriquecimento Geográfico

Onde: Chunks da PROC-042 com tabela regional

Problema resolvido: Query "frete para Manaus" não conectava com "região Norte" nos documentos — o modelo inglês não associa cidade a região.

Como: Detecta padrão | Norte | na tabela e acrescenta:

Cidades atendidas por região: - Norte: Manaus, Belém, Porto Velho, ... - Nordeste: Salvador, Recife, Fortaleza, ...

📊 Enriquecimento de Tabelas

Onde: Todos os chunks com tabelas markdown

Problema resolvido: Células | col | val | têm embedding fraco — a tabela de SLAs pontuava abaixo do FAQ informal para queries sobre SLA Gold.

Como: Converte cada linha em texto narrativo:

Resumo textual da tabela: Tempo de resposta (gerais) — Gold: Até 2h úteis, Silver: Até 4h úteis, Standard: Até 8h úteis

🔄 Tratamento de Versões Conflitantes

✅ Ambas as versões são indexadas: PROC-042 v1 e v2 coexistem no banco. O campo is_latest marca qual é a versão mais recente. O prompt_builder exibe [VERSÃO ANTERIOR] no bloco do documento para ativar a instrução do system prompt de priorizar a versão mais recente.
# Indexação com resolução de versões group[0]["is_latest"] = "true" # versão mais recente for old_doc in group[1:]: old_doc["is_latest"] = "false" # versões anteriores — ainda indexadas # Ambas processadas — LLM prioriza a mais recente via prompt docs_to_process = parsed_docs

🔍 Fase 2: Busca e Recuperação (Retrieval)

2
Script: retriever.py

🎯 Objetivo

Receber uma pergunta do usuário e buscar os chunks mais similares no ChromaDB, retornando os N mais relevantes acima do threshold de score.

⚙️ Modelo de Embedding

all-MiniLM-L6-v2 (HuggingFaceEmbeddings)
• Dimensões: 384  |  Velocidade: ~14.200 sentenças/segundo
• Limitação conhecida: Modelo treinado predominantemente em inglês — scores para documentos em português são uniformemente baixos (~0.35–0.65). Threshold reduzido para 0.35 por esse motivo.
• Alternativa recomendada: paraphrase-multilingual-MiniLM-L12-v2 para scores mais discriminativos em português (requer reindexação).

🔧 Parâmetros da Função

def buscar_chunks( pergunta: str, vectorstore: Chroma, n: int = 5, # chunks retornados score_minimo: float = 0.35, # threshold — reduzido de 0.40; modelo inglês gera scores baixos filtro_metadados: dict | None = None ) -> list[dict]: # 1. Busca n*3 candidatos no ChromaDB (15 candidatos para n=5) raw_results = vectorstore.similarity_search_with_relevance_scores( query=pergunta, k=n * 3 ) # 2. Ordena por score decrescente # 3. Filtra: score >= score_minimo → valid_results # 4. Retorna os top-n válidos (sem pad — contexto vazio aciona fallback do prompt)

📌 Por que k = n×3 (e não n×2)?

✅ Mais candidatos = mais cobertura: Com k=10 (n×2), o chunk de multiplicadores regionais da PROC-042 (seção 2.1) ficava nas posições 6–10 do ranking — fora do top-5 retornado. Com k=15 (n×3), o chunk entra na janela de avaliação, e o filtro de score decide se ele é relevante o suficiente para compor o contexto.

❌ Sem pad forçado (removido)

Removido: O pad para mínimo de 3 chunks foi eliminado. Quando não há chunks com score ≥ 0.35, a função retorna lista vazia — o prompt_builder exibe [SEM CONTEXTO] e o LLM responde com a frase padronizada de "não encontrei a informação". Injetar chunks de baixa qualidade introduzia ruído (ex: FAQ-22 sobre seguro de carga sendo entregue para perguntas sobre prazo de devolução).

📝 Fase 3: Montagem de Prompt

3
Script: prompt_builder.py

🎯 Objetivo

Receber os chunks recuperados e montar um prompt estruturado com tags XML, pronto para envio ao Claude. Inclui sinalização automática de versão anterior para ativar a instrução de conflito do system prompt.

⚙️ Estrutura do Prompt

Se houver versões diferentes do mesmo documento, priorize explicitamente a mais recente e avise sobre a divergência 4. Se não encontrar a resposta: "Não encontrei essa informação nos documentos disponíveis. Consulte [responsavel]..." </system> <documentos> --- Documento [1] --- Fonte : PROC-042-v2-frete-especial-revisado.md Versão : 2.0 Emissão : 10/11/2023 Responsável: Diretoria Comercial Score : 0.58 ### 2.1. Fórmula de cálculo ... --- Fim do Documento [2] --- </documentos> <pergunta> Frete para 600kg para Manaus? </pergunta>

🚨 Sinalização de Versão Anterior

✅ Ativação explícita da instrução 3: Quando is_latest == "false", o bloco do documento recebe o aviso [VERSÃO ANTERIOR — priorize a versão mais recente do mesmo documento]. Sem esse marcador, o LLM precisaria inferir qual versão é mais recente comparando campos de data — possível, mas não garantido.

🔧 Controle de Tokens e Avisos

Limite de Contexto: 3.000 tokens (~12.000 caracteres)
Estimativa: 1 token ≈ 4 caracteres
Truncamento: Se exceder, inclui apenas os chunks mais relevantes e registra aviso
Sem contexto: Insere [SEM CONTEXTO] — LLM aciona resposta padronizada

🏆 Diferenciais da Pipeline NovaTech v3

✅ Nível de Produção: Esta pipeline possui características profissionais que vão além de um "Hello World" de RAG — incluindo enriquecimento semântico, gestão de versões e rastreabilidade completa.

🗂️ Chunking Estrutural

Divisão por cabeçalhos markdown respeita os limites semânticos do documento — cada subseção vira um chunk íntegro e respondível por si só.

🌍 Enriquecimento Geográfico

Queries com nome de cidade conectam ao chunk de região sem depender de sinônimos no modelo de embedding — resolve gap semântico sem trocar o modelo.

📊 Enriquecimento de Tabelas

Tabelas markdown são convertidas em texto narrativo no momento da indexação — o LLM recebe os dados em formato de linguagem natural no contexto.

🔄 Coexistência de Versões

PROC-042 v1 e v2 ambas indexadas com flag is_latest — o prompt sinaliza explicitamente a versão anterior para que o LLM priorize a mais recente.

📍 Rastreabilidade por Seção

Metadado secao mostra exatamente de qual subseção do documento o chunk veio — auditoria vai além de "qual arquivo" para "qual parágrafo".

🛡️ Contexto Limpo

Sem pad forçado — quando não há chunks relevantes, o LLM recebe contexto vazio e aciona a resposta padronizada em vez de receber ruído como resposta.

📊 Modo Incremental + Força

Reprocessamento inteligente pula documentos já indexados. Opção forcar_reindex garante que mudanças de estratégia sejam aplicadas ao banco inteiro.

⚡ Performance Local

Modelo de embedding leve rodando sem GPU, 5–10× mais rápido que APIs externas. ChromaDB com HNSW para busca aproximada em milissegundos.

📚 Glossário Técnico

Termo Definição
Chunk Fragmento de texto resultante da divisão de um documento. Na v3, cada chunk corresponde a uma seção ou subseção semântica (ex: "3.2. Exceções ao prazo geral" completa).
Embedding Representação numérica (vetor) de um texto que captura seu significado semântico. Textos com significado similar ficam próximos no espaço vetorial.
Similaridade Coseno Métrica de distância entre vetores que mede o ângulo entre eles — independente do tamanho do texto. Scores variam de 0.0 (sem relação) a 1.0 (idênticos).
Threshold Score mínimo aceitável (0.35 nesta pipeline). Chunks abaixo desse valor são descartados — considerados semanticamente distantes da query.
Enriquecimento Adição de texto complementar ao chunk durante a indexação para melhorar o embedding. Exemplos: cidades por região, resumo textual de tabelas.
is_latest Metadado que marca se um chunk vem da versão mais recente de um documento ("true") ou de uma versão anterior ("false"). Usado pelo prompt_builder para sinalizar conflito.
Vector Store Banco de dados especializado em armazenar e buscar vetores por similaridade. Usa índice HNSW para busca aproximada eficiente. Nesta pipeline: ChromaDB local.
System Prompt Instrução inicial que define o comportamento do LLM — persona, regras anti-alucinação, forma de citar fontes e como tratar conflitos de versão.
RAG Retrieval-Augmented Generation — técnica que combina busca vetorial com geração de texto para que o LLM responda com base em documentos específicos, não apenas no treinamento.
Hallucination Quando o LLM inventa informações que não estão no contexto fornecido. Prevenida nesta pipeline pelo system prompt e por não injetar chunks de baixa qualidade.
